## Executive Summary

This Stage 1 Baseline Audit rigorously analyzes the infrastructure, test suite, evaluation harness, telemetry, and historical benchmarks of the Aster & Row AI Support Agent. 

The primary objective was **not** to celebrate passing marks, but to probe the architecture for silent failures, methodological blind spots, observability gaps, and production vulnerabilities.

### Key Audit Findings

1. **Pytest Suite Health**: The test suite is fast and 100% passing (224/224 passed in 44.87s). All 36 test modules are self-contained; unit and integration tests strictly mock LLM providers and HTTP requests using `unittest.mock.patch` with zero external network dependencies.
2. **Critical Evaluation Discovery — Silent Fallback Masking**: In **all committed evaluation result files** (`baseline.json`, `final.json`, `novel_baseline.json`, `final_novel.json`), the **Provider Generation Failure Rate was 100.0%** (16/16 turns in visible cases, 9/9 turns in regression cases) and the **Deterministic Fallback Rate was 100.0%**. The evaluation suite awarded 93.3% to 100.0% pass rates entirely to hardcoded fallback template strings generated by `OutputValidator.build_fallback()` because the evaluation harness lacks assertions verifying that the LLM actually generated the response.
3. **Adversarial Probes Lack Assertions**: `evaluation/probe_adversarial.py` merely executes 5 adversarial test scenarios and dumps output logs to `adversarial_probes.json`. It performs zero programmatic assertions on safety, PII disclosure, or refusal compliance.
4. **Severe Observability Gaps**: End-to-end request latency is unmeasured. Latencies for routing, entity resolution, order lookup, retrieval, knowledge resolution, and output validation are entirely absent from telemetry. Only LLM generation time (`generation_latency_ms`) is tracked.
5. **Reproducibility Verified**: Baseline evaluations were cleanly reproduced without overwriting original files. The current codebase achieves 15/15 (100.0%) on visible cases and 8/8 (100.0%) on novel regression cases under deterministic fallback conditions.

### 3.3 Systematic Answers to Core Evaluation Questions

#### 1. What exactly constitutes a passing scenario?
In `EvaluationHarness.evaluate_case()`, a scenario passes if and only if `len(failures) == 0`. Failures are appended when any configured expectation in `case.expect` is violated:
- `handoff`: matches `last_state.handoff_recommended`.
- `expected_decision_state`: matches `last_state.decision.state`.
- `tool` & `tool_arguments`: matches route type and order ID.
- `required_sources`: verifies every required document ID is in `last_state.evidence_pack.approved_evidence`.
- `forbidden_sources_as_authority`: verifies no forbidden document is approved.
- `must_not_silently_choose_one`: checks `conflict_detected == True` and decision is `CONFLICT` or `HANDOFF`.
- `must_include`: checks concept presence via `text_contains_concept()` in the **final turn message**.
- `must_not_include`: checks case-insensitive absence of forbidden text in the **final turn message**.
- `must_refuse_to_disclose`: checks specific substrings (e.g. `ava.morgan`).
- `must_ask_for`: checks concept presence in clarification queries.

#### 2. Are assertions based on actual application behavior?
Yes. Assertions inspect `AgentState` generated by `AgentOrchestrator.process_turn()`, which runs the real routing, retrieval, knowledge resolution, and decision engine pipeline. However, several checks are tailored to specific fixtures (e.g. hardcoding `"ava.morgan"` in line 313 of `harness.py`).

#### 3. Are any LLM providers mocked during evaluation?
No. When `EvaluationHarness()` is initialized without arguments, it instantiates `AgentOrchestrator()`, which invokes `get_llm_provider()` using `.env` configurations.

#### 4. Can provider failures still produce passing scenarios?
**YES (CRITICAL FLAW)**. When the LLM provider fails, `AgentOrchestrator` catches the exception and calls `OutputValidator.build_fallback(gen_request, reason=...)`. This creates a deterministic, highly structured answer containing the exact order details, policy citations, and phrasing expected by the test cases. Because `EvaluationHarness` does not assert `is_fallback == False`, the scenario passes despite total LLM failure.

#### 5. Are fallback responses counted as successful generations?
**YES (CRITICAL FLAW)**. While `TurnResult.is_fallback` is recorded in the result JSON, it has zero impact on `CaseResult.passed`. A run where 100% of LLM calls fail can achieve a 100% pass score.

#### 6. Are citations and groundedness independently validated?
**NO**. `required_sources` only asserts that the `EvidencePack` approved the chunk. There is no Natural Language Inference (NLI) model, lexical overlap verification, or hallucination evaluator confirming that the claims in the generated natural language response are actually supported by the cited chunks.

#### 7. Are adversarial probes actually asserting expected behavior, or merely recording outputs?
**MERELY RECORDING OUTPUTS**. `evaluation/probe_adversarial.py` contains zero assertions. It loops over 5 probe queries, extracts public response fields, and dumps them into `evaluation/results/adversarial_probes.json`. It provides no pass/fail verdict.

#### 8. Are existing result files reproducible?
Yes. Running `evaluate.py` with `LLM_PROVIDER=flexible` (matching the environment of the original runs) produces identical deterministic outputs and 100% pass rates.

## 7. Provider & Fallback Reliability Analysis

### 7.1 Fallback Chain Architecture
The active LLM generation layer in `src/llm/fallback.py` defines a 3-tier cascade:
```
Primary Provider (Groq openai/gpt-oss-120b)
       │
       ▼ (on Exception / HTTP 429 / Timeout)
Secondary Provider (Groq openai/gpt-oss-20b)
       │
       ▼ (on Exception / HTTP 429 / Timeout)
Deterministic Fallback (OutputValidator.build_fallback)
```

### 7.2 The Provider Disconnect
1. **Model ID Mismatch**: In `.env.example` and `src/core/config.py`, the Groq models are configured as `openai/gpt-oss-120b` and `openai/gpt-oss-20b`. These are not standard Groq API model names (Groq hosts `llama-3.3-70b-versatile`, `llama-3.1-8b-instant`, `mixtral-8x7b-32768`).
2. **Missing External Call Pre-requisites**: Calling Groq or Gemini endpoints involves real network requests and token usage. Under Rule 9, no paid/external requests were executed during this audit.

## 8. Evaluation Methodology Weaknesses

1. **Silent Fallback Masking**: The single biggest flaw in the current evaluation system. When an LLM fails, the system succeeds. This creates inverted incentives where broken LLM integrations yield higher reliability scores than working models that produce natural linguistic variation.
2. **Final-Turn Only Evaluation**: In multi-turn scenarios (e.g. `canada-multiturn`), assertions are only evaluated against the **final turn**. Intermediate turns can hallucinate, leak data, or fail completely without failing the test case.
3. **Keyword-Heuristic Text Assertions**: `text_contains_concept()` relies on simple string containment and token subsets. It cannot assess tone, grammar, coherence, or contextual correctness.
4. **Hardcoded Customer Assertions**: Lines 313–320 of `evaluation/harness.py` explicitly check for `"ava.morgan"`. If an attack leaks a different customer's email (e.g. `marcus.vance@example.com`), the test passes.
5. **No Groundedness or Citation Faithfulness Checks**: Citations are logged as strings, but never validated against the actual sentence claims in the LLM response.
6. **Unasserted Adversarial Probes**: Adversarial probes do not fail when safety boundaries are breached because `probe_adversarial.py` does not assert anything.

---

## 9. Potential Production Risks

1. **Zero Real-World LLM Validation**: The system has never been evaluated under non-deterministic LLM output conditions. Real models may use synonyms that fail `must_include` checks or trigger false positives in `OutputValidator`.
2. **Severe Latency Blindness**: Without instrumentation for routing, vector search, or database access, a 5-second retrieval spike in production would go completely undetected until users churn.
3. **Regex PII Filter Vulnerabilities**: PII detection relies on basic regular expressions. Adversarial prompt injections using Leetspeak, base64, or spaced text could easily bypass them.
4. **Provider Vendor Lock-In & Model Deprecation**: Relying on unverified model identifiers (`openai/gpt-oss-120b`) on Groq introduces immediate initialization failures if live generation is enabled.
